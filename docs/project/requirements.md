# 个人健康日志：项目规格

2026-10-24 两轮评审确认的产品规格。此文件与同目录 `m1-plan.md` 为两端共同的版本源；本地交接文档是快照。领域词汇见各仓库根目录 CONTEXT.md，长期决策见 docs/adr/。

已发布的[主规格与子任务总览](https://github.com/DaisenHo/HealthLog/issues/1)为实施入口；优先从 [T01：Web 账户语言切换](https://github.com/DaisenHo/HealthLog/issues/2)开始，后续按子任务的原生阻塞关系推进。

用途为个人非商业使用。保留两端上游许可证、Required Notice、Git 历史和 upstream。上游为 https://github.com/MBombeck/HealthLog 与 https://github.com/MBombeck/healthlog-iOS；两个个人 Fork 继续保持 Public。

## 1. 已确认的产品边界

HealthLog 负责基础档案、通用目标与习惯打卡、数据图表、任务达成统计和日报；Apple 健康负责约定的血压录入及提醒流程。用药计划、服用记录和提醒的管理入口本次重新开放：先核对当前 HealthLog 功能，与 Apple 健康逐项比较，再选择沿用或替代方案。每种药品避免重复维护两套录入和提醒，选择前保留现有功能。

上游已有双向同步、手动录入和用药提醒。这是后续适配需要处理的差异：M1 仅做语言支持并保留上游行为；在 M2/M3 按领域逐步建立个人只读工作流；M5 的用药工作流先经过能力比较和来源选择。优先复用已有设置来避免重复写入/提醒，必要时做最小修改；已有数据和功能不能被直接删除。

用户最初提出的“在本 App 录入血压并写入 Apple 健康及小米运动健康”已被后续决定替代。小米运动健康反向写入血压仅作未来探索，不属于首期，也不是首期验收依赖。

### 2026-10-24 第一轮评审已确认

1. 语言偏好归账户统一管理，覆盖登录后的 Web、iOS 和后台日报；未登录时跟随系统，离线时使用本机缓存。首期修改账户语言需联网，离线只使用缓存语言。
2. 日报完成率统计当天到期的目标。周/月目标在周期中途只展示进度，周期结束才判定结果并进入到期日的统计。
3. 日报按时生成。尚未同步或无法判断的目标显示“待确认”（能识别同步延迟时说明“待同步”），分别展示已完成、未完成和待确认数量；存在待确认项时不显示确定的总完成率。数据到达后修订原报表，默认不重复推送。
4. 设备链路按指标降级：可用项先交付，不可用项明确标注并延期；引入手动替代录入前再确认。
5. 正式环境采用持续运行的服务器，本机用于开发。具体主机、部署地址和推送凭据在部署阶段配置；日报默认时间见第二轮决定。本次确认不创建或购买服务器。

### 2026-10-24 第二轮评审已确认

6. 时间边界：固定采用账户时区，默认 `Asia/Shanghai`；周一开始一周，月份为自然月。跨夜睡眠归醒来当天，午睡归结束当天，分期片段不得重复计数。旅行不自动改变统计时区，历史报表保留当时口径。
7. 目标变更：新增目标从下个完整周期开始；阈值修改下周期生效。停用立即停止相关 HealthLog 通用提醒，当前未到期目标记为“已取消”并排除统计；已经结束的周期保留原规则，补录或更正记录仍可修订结果。本条不管理 Apple 健康中的用药安排。
8. 服药目标：支持用户明确设置“指定药品每周期记录 N 次已服用”的目标，名称为“服药记录目标”，不是“服药依从率”。具体用药管理归属本次重新开放，待功能比较后选择；无论选择哪一端，HealthLog 都不根据药品名称或历史次数猜测应服次数。
9. 缺失数据：数据关联目标证据不足时持续显示“待确认”，不因等待超时自动转失败；普通手动打卡目标到期未打卡算未完成。没有到期目标时显示“不适用”，不显示 0% 或 100%。
10. 离线语言：使用本机缓存；修改账户语言需联网，成功后按账户偏好同步两端和后台日报。
11. 日报推送：默认账户时区每天 08:00 生成前一天日报，时间可调整。锁屏仅显示“昨日健康日报已生成”，详情在 App 查看。服务恢复后补齐历史报表，只补发最近一份通知；同一日报修订默认不重复推送。

### 用药选择的前置验收

能力比较见同目录 `medication-workflow-comparison.md`。选择用药来源前，分别核验当前系统的原生计划/记录/提醒/统计能力、Apple 健康自身能力，以及两者公开 API 能连接的范围。Apple 界面能做的功能不等于 HealthLog 已能读取或回写；当前导入器的过滤行为也不等于平台能力上限。

## 2. 数据流与归属

| 数据/行为        | 用户侧来源                                                 | 到 HealthLog 的路径                                                  | 主要责任                                                 |
| ---------------- | ---------------------------------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------- |
| 心率、睡眠、步数 | 小米手环 11、小米运动健康                                  | 小米运动健康 → Apple 健康 → HealthKit → HealthLog iOS → 服务端       | 验证来源写入能力与去重；不假定全量或实时同步             |
| 体重             | 米家体脂秤 S400、米家                                      | 米家 → Apple 健康 → HealthKit → HealthLog iOS → 服务端               | 首期要求体重，不擅自扩展到所有体脂指标                   |
| 血压             | 外部测量后在 Apple 健康手动录入                            | HealthKit 血压关联样本 → iOS → 服务端                                | Apple 健康管理提醒与录入；HealthLog 只读统计             |
| 药品、服用记录   | 待比较后选择 HealthLog 或 Apple 健康；每种药品明确单一来源 | HealthLog 原生记录进入服务端；选择 Apple 来源时经 HealthKit 读取事件 | 比较计划、记录、提醒、统计与同步；不假定存在完整双向同步 |
| 基础资料         | HealthLog                                                  | iOS/Web → 现有 API → 数据库                                          | 出生日期、性别、身高、已确诊疾病（例如乙肝、高血压）     |
| 通用目标与习惯   | HealthLog                                                  | iOS/Web → 现有或扩展 API                                             | 每日/每周/每月，数据关联或手动打卡                       |
| 日报             | HealthLog 服务端                                           | 数据聚合 → 报表 → 推送 → iOS/Web 查看                                | 用户指定时间总结前一天，允许迟到数据修订                 |

所有链路均为目标架构，尚未做设备实测。Apple 健康没有收到的厂商数据，HealthLog 不能通过 HealthKit 凭空取得。M2 保留设备地区/型号、固件、iPhone/iOS、米家及小米运动健康版本、权限与来源截图作为本地验收证据，不把真实健康信息提交到 Git。

## 5. 后续实现的数据约束

- 同步：沿用上游 external ID 和同步协议，先验证已有去重；样本身份、同步来源、事件时间和入库时间分别保存。不能只按数值+日期去重，以免吞掉真实的重复测量。
- 增量：使用现有 HealthKit anchor/队列；成功入库后才能推进相应处理进度。断网重放、部分失败、样本删除/更正均需验证；多个来源的步数/睡眠不能简单相加。
- 血压：按 HealthKit correlation 配对收缩压和舒张压，不按相近时间盲配；沿用可核验的单位换算。
- 服药：药品概念标识与事件身份分开；按计划时间和实际服用时间保留原意。无数据可能来自未授权、同步延迟或确实未记录，不能自动标注“未服药”。
- 通用目标：复用现有目标/任务模型，不先造可配置规则语言。最小范围是周期、阈值/次数、关联类型或手动打卡、启停、时区和完成状态。
- 提醒：Apple 健康负责约定的血压提醒；用药提醒来源待功能比较后决定。HealthLog 的通用目标/日报与被选定来源协调，关联目标不得隐含再开启同类提醒。
- 报表：按用户时区计算自然日、周、月；保留 UTC 事件时间与时区语义，不以服务器本地时区切日。按本节已确认的时间归属、周期和目标变更规则实现；采用账户时区而非设备临时所在地时区。
- 已确认的统计口径：完成率仅统计当天到期的有效目标；有待确认项时暂不显示确定的总完成率，周/月进行中目标单列进度。没有到期目标时显示“不适用”；其余已确认规则见第二轮决定。
- 日报可靠性：服务端调度生成，按用户+统计日避免重复任务；报表携带数据截止时间与版本，迟到数据可修订。重试与回执可观察；iOS 后台调度、APNs 接收及阅读不是严格准点保证。
- 数据保护：沿用鉴权与用户隔离；远程传输采用 HTTPS；不在日志、PR、示例、测试或截图中暴露真实健康记录和密钥。数据库迁移先验证备份与回滚，不重置现有数据。

## 6. 已核验与待核验的外部能力

已核验：Apple 提供 `HKUserAnnotatedMedication`、`HKMedicationDoseEvent` 和按药品读取授权；授权药品后可读取该药品的剂量事件。`HKMedicationDoseEvent` 的 Apple 文档元数据注明从 iOS 26.0 起可用。保留 iOS 18 基线时必须做 availability 分支，旧系统展示“系统版本不支持读取”，不得静默建立另一套服药录入。

来源：[Apple Medications API 讲解](https://developer.apple.com/videos/play/wwdc2025/321/)、[HKMedicationDoseEvent](https://developer.apple.com/documentation/healthkit/hkmedicationdoseevent)、[Apple 官方文档元数据](https://developer.apple.com/tutorials/data/documentation/healthkit/hkmedicationdoseevent.json)。Apple 还明确说明剂量事件可补记、删除并重新保存，增量同步必须处理这些变更。

已核对的上游实现：`healthlog-iOS/HealthLog/Stores/MedicationHealthSyncStore.swift` 和 `HealthLog/Services/HealthKit/AppleHealthMedicationReader.swift` 已有默认关闭的独立授权、首次同步及剂量事件观察。M5 先验收这些现有能力，再补修订/删除、目标关联及旧系统不可用说明；现有代码低于 iOS 26 隐藏入口。

待核验：用户手机上的 Apple 健康能否按所需长期频率提供血压测量提醒；不能把特定系统/设备的短期血压记录流程等同于通用长期提醒。按现有决定先验证 Apple 健康；如果不能满足，报告具体差距再由用户决定替代方式，不擅自增加 HealthLog 重复提醒。

待核验：小米手环 11、小米运动健康及米家 S400 的准确数据出口、地区/版本限制、睡眠阶段粒度及后台延迟。尚未做硬件验证；不能把旧机型或其他地区经验当作已兼容结论。

## 8. 实现前验证关口

设备实测、Apple 健康血压提醒可用性、服药事件删除/更正传播、数据来源去重、推送签名与恢复补发仍须验证。它们是后续阶段的技术验收项，不是已经完成的功能。精确 API、数据覆盖判据及去重实现以源码和真机证据为准，不能仅凭空结果宣称用户未完成。

M1 优先开展；按阶段复用已验证的上游功能。执行 M2–M6 时，若事实与本规格前提不符，记录具体限制并按已确认的降级边界处理；超出边界的替代方案再与用户确认。
